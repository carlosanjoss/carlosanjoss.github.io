Building a multi-source social data pipeline without losing traceability

A practical way to separate collection, normalization, and analytics while keeping every transformation understandable and reproducible.

Engineering note8 min readCarlos Eduardo

Collecting data from one platform is an integration task. Collecting comparable data from seven platforms is a modeling problem. Each source arrives with its own identifiers, timestamps, nesting rules, rate limits, and definitions of a “post” or “comment.” If those differences are flattened too early, useful context disappears. If they are never reconciled, analysis becomes a collection of special cases.

In the Social Data Pipeline project, I use a layered architecture to preserve both realities: the original source and a consistent analytical view. The goal is not only to move data. It is to make later results traceable back to what was collected, how it was transformed, and which version of the pipeline produced it.

Three layers, three responsibilities

The pipeline separates storage by responsibility. MongoDB acts as a raw lake for source-shaped documents. PostgreSQL holds normalized and validated entities. DuckDB provides an analytical warehouse organized for aggregation and exploration.

  • Raw layer: retain the source payload with minimal transformation and enough metadata to replay normalization.
  • Normalized layer: represent shared concepts such as platforms, authors, posts, comments, and collection runs through explicit relationships.
  • Analytical layer: reshape trusted records into facts and dimensions for fast, understandable queries.
Raw data protects evidence. Normalized data protects meaning. Analytical data protects usability.

This separation also creates a useful failure boundary. A temporary issue in a downstream model does not require another collection run. A change to the analytical schema does not modify the original documents. Each layer can evolve while its inputs remain inspectable.

Designing for heterogeneous sources

Connectors run independently and produce a small, predictable contract. Platform-specific logic stays close to the connector: pagination, nested replies, source identifiers, and timestamp parsing. Shared validation and persistence happen after that boundary.

Deduplication should rely on native identifiers whenever they are trustworthy. In this project, overlapping Reddit inputs can be reconciled by their platform IDs before normalized persistence. This is safer than comparing text, which can change through editing, formatting, or preprocessing.

Language as a data constraint

The normalized scope is Portuguese-language content. Instead of treating this only as a query filter, the final relational layer makes the language expectation explicit. That turns a research decision into an enforceable data contract and prevents future ingestion changes from silently broadening the dataset.

Reproducibility is an operational feature

A reproducible pipeline records more than rows. Collection runs, source names, timestamps, configuration, and transformation versions are part of the result. Logs should answer three questions quickly: what ran, what changed, and what failed.

Idempotent writes are equally important. A rerun should update or skip known records according to a documented rule, not create a second interpretation of the same source event. This makes recovery routine and reduces the temptation to repair datasets manually.

What this architecture enables

Once the data layers are stable, downstream systems become simpler. A local LLM classifier can read normalized text without knowing the details of every scraper. An NLI stage can focus on its hypotheses. A Streamlit dashboard can query consistent views rather than reproduce transformation logic.

The broader lesson is that data architecture shapes the quality of AI evaluation. Traceable inputs make model errors explainable, comparisons repeatable, and results easier to communicate. The pipeline is therefore not a preliminary step around the model — it is part of the model’s evidence.
