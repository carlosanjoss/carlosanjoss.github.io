Evaluating local LLMs beyond a single accuracy score

Reliable evaluation starts before the metric: with structured outputs, explicit failure states, versioned prompts, and evidence that survives every experiment.

Research note7 min readCarlos Eduardo

A local language model can return an answer that looks plausible while still being impossible to evaluate consistently. Free-form responses hide ambiguity in formatting, skipped fields, contradictory labels, and silent failures. Before comparing models, I first make the inference process measurable.

In the Gemma Hate Inference project, the model produces structured decisions for Portuguese-language content. The pipeline separates the binary decision from the detailed category stage and validates the result before persistence. Invalid JSON, inconsistent fields, and server errors remain errors; they are not quietly converted into negative predictions.

Start with a strict output contract

A compact schema reduces the number of ways a response can be “almost correct.” The first stage answers a narrow question and records its confidence. Only positive candidates enter the detailed stage, which adds categories, target, textual evidence, and a short justification.

This structure has two benefits. It makes the model’s behavior easier to parse, and it makes disagreement easier to inspect. A derived label should come from one authoritative decision rather than asking the model to repeat the same answer in multiple fields.

An evaluation dataset should include model failures as first-class outcomes, not hide them inside the negative class.

Store the evidence of every run

A prediction without context is difficult to reproduce. For each analyzed item, the pipeline records the model, prompt version, analyzed text, content hash, raw response, attempt count, timing, and status. That evidence allows two experiments to be compared without relying on memory or notebook state.

Versioned prompts matter because wording is part of the model configuration. Changing a definition, example, or output instruction can shift the distribution even when the model weights stay the same.

Use a metric set, not a headline number

Accuracy can be useful, but it rarely explains the cost of errors. I monitor precision, recall, F1-score, specificity, and accuracy, then connect those measures to a confusion matrix and sample-level error analysis.

  • Precision reveals how often flagged content is correct.
  • Recall shows how much relevant content the system finds.
  • Specificity measures how reliably it leaves negative examples alone.
  • F1-score summarizes the precision-recall balance but does not replace inspecting each side.

The right operating point depends on the use case. A research dashboard, a moderation queue, and an automated decision each assign different costs to false positives and false negatives.

Add a second reasoning layer

NLI provides another way to test semantic hypotheses after the initial classifier. In the NLI Radar project, separate layers evaluate intensity and discourse dimensions, persist hypothesis scores, and link results back to the exact upstream classification that released the content for analysis.

This does not make the system automatically correct. It makes the reasoning path more observable. When layers disagree, the disagreement becomes a candidate for analysis rather than an invisible averaging effect.

The practical evaluation loop

A useful loop is simple: freeze the dataset, version the configuration, run inference, calculate metrics, inspect errors, revise one variable, and rerun. The discipline comes from changing one thing at a time and preserving enough metadata to explain the difference.

Local LLM evaluation is therefore both a modeling task and an engineering task. Strong metrics begin with dependable data contracts, explicit error semantics, and a traceable experiment history.
